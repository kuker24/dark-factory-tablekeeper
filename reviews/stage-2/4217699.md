## Findings

### F6 — `confirmation-tables` and `reservation-tables` elements are absent (UI, blocking)

- Requirement: stage-2 req 37; spec stage-2.md:227-228 ("`confirmation-tables` text contains
  every table label in the reservation"; "`reservation-tables` on the lookup screen, same").
- Evidence: after a confirmed pair booking the DOM contains `confirmation`,
  `confirmation-reference`, `confirmation-details` but **no `confirmation-tables`**
  (`app.js:311-343`, `showConfirmation`). After lookup with a valid reference the DOM
  contains `reservation-detail`, `reservation-status`, `reservation-cancel-button` but
  **no `reservation-tables`** (`app.js:475-506`, `showReservationDetail`). Direct DOM probe:
  `confirmation-tables present: False`, `reservation-tables present: False`. Labels do appear
  inside `confirmation-details` text (`Zum Anker · tables 1 + 2 · 19:00`) but that is a
  different, unspecified testid.
- Consequence: UI probe U8 fails; both required elements are missing.
- Root cause: the dynamic-DOM refactor (`4217699`) recreated the confirmation/detail
  surfaces without the two contract-mandated testids that existed before.

### F7 — Lost booking response shows no `booking-uncertain` (and no feedback at all) (UI, blocking)

- Requirement: stage-2 req 5; spec stage-2.md:30-34 — a lost booking response (including
  after commit) shows nonempty `booking-uncertain` text, without `booking-error` or a new
  confirmation; the unchanged form retries with the same idempotency key and body; a
  successful retry removes uncertainty/error and shows the original reference.
- Evidence: `onSubmitBooking` (`app.js:402-455`) never creates or shows a
  `booking-uncertain` element; there is no such testid anywhere in the client
  (`grep booking-uncertain static/app.js` → none). On a dropped response it silently
  auto-retries with the same key/body and, when that retry also fails (network `api()`
  returns `null`), falls through with no UI update. Direct browser probe with the POST
  response aborted after server commit:
  `booking-uncertain present: False`, `booking-error present: False`,
  `confirmation present: False`, `booking-form present: True` — the user receives no
  uncertain indicator and no error.
- Consequence: UI probe U11 fails at `wait_for_selector(booking-uncertain)`; the mandated
  uncertain state is neither shown nor visually distinct.
- Required: show `booking-uncertain` (nonempty) when the response is lost without
  `booking-error`/confirmation, keep the unchanged form, retry same key+body, and on success
  clear the uncertain/error elements and show the original reference.

## Check-gaming review

Read the full diff `d50dbf7..4217699`. The move of booking/lookup surfaces into JS-created
nodes is a legitimate response to the shipped tests' `query_selector(...) is None`
assertions for inactive surfaces, not gaming: the elements are created on first use and the
availability grid stays in static HTML as the tests expect. No edits to shipped checks.
However, this refactor silently dropped the `confirmation-tables`/`reservation-tables`
testids and the `booking-uncertain` state, neither of which the shipped checks exercise —
which is why the harness reports 25/25 at this revision while two binding requirements are
violated.
